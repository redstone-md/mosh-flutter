## Attribution

The instruction export contains 12,494 selected weights, one fewer than its
summary. Attribution below consistently uses the raw instruction denominator.
These proportions are sample weights, not process CPU milliseconds or recovered
caller stacks.

- Go Edwards25519 leaves fall from 898/10,430 (8.61%) to 52/12,494 (0.42%).
  This supports removal of the previous repeated-verification hotspot; it
  does not establish a whole-process improvement.
- Moss accounts for 3,372 weights, kernel code for 3,649, Rust for 1,477,
  Flutter for 1,180 and unmapped user code for 1,626. Exact current Go ranges
  resolve 3,365 Moss weights; the original Rust PDB resolves all Rust weights.
- Go's remaining leaves include memory copying, allocation/GC, JSON encoding,
  map iteration and scheduling. `MeshInfoJSON` itself has 54 flat weights.
  Flat samples do not attribute its callers' cumulative cost.
- Approximate CPU/network overlap correlation is 0.41. This is an association,
  not evidence identifying a particular driver, protocol or UI operation.

Stale application binaries and the old dominant announcement-verification
hotspot are rejected as explanations for this capture. Repeated native query
work, public-mesh network activity and different maturity/state remain separate
candidate contributors. The owner's message-count answer does not support a
thousand-message workload assumption.

## Independent native query probe

A disposable Linux fixture uses eight acknowledged offline DMs, two groups and
one channel. Each DM initially has one message. The existing optimized Rust
worker's sources are identical to the current Mosh Rust sources. It loads
current Moss `82eb8b6`, built with Go 1.25.9. A private Go overlay adds CPU and
allocation sampling plus an atomic `MeshInfoJSON` entry counter. Production
sources, routing decisions, keys and settings are unchanged. No kernel or
power settings are tuned. Fictional message snapshots retain their golden
SHA-256 throughout the run.

After six minutes of warmup, a 90-second profile counts 1,117 mesh queries.
Sampled allocation deltas attribute 62.93 MiB of 119.74 MiB (52.55%) to
`MeshInfoJSON`. Exact Go allocation counters increase by 136,310,048 bytes;
sampled heap profiles can lag the latest collection and are not exact byte
counters. The direct mesh-query CPU path accounts for only 0.11 of 2.44 sampled
CPU seconds. Go's profiler also samples foreign native code; the total is not
exclusively Go CPU. Native process counters average 3.50% of one core, with
nineteen peers in this interval.

The reused harness requests group and channel lists twice per second, whereas
the current Flutter auto-poller requests each kind once per second. Its
12.41 queries/s are therefore a controlled harness observation, not the owner
application's measured request rate. It demonstrates query allocation cost but
does not prove the whole-application CPU cause. The corrected control uses the
current once-per-kind schedule and compares it with omitted UI requests in the
same process while keeping normal DM background service and the Moss node alive.

The corrected control completes four consecutive 90-second windows after six
minutes of warmup. Each UI window requests names, one list of each conversation
kind and the selected DM once per second. Message goldens match throughout.

| Consecutive native window | CPU, one core | Mesh queries | Allocated Go memory | Peers, start → end |
| --- | ---: | ---: | ---: | ---: |
| UI requests | 3.144% | 851 | 101.90 MiB | 13 → 13 |
| UI requests omitted | 2.489% | 228 | 70.60 MiB | 13 → 13 |
| UI requests omitted | 3.300% | 227 | 99.68 MiB | 13 → 19 |
| UI requests | 4.544% | 850 | 156.03 MiB | 19 → 23 |

Go memory allocation is the exact cumulative allocation-counter delta, not
retained heap or working set. Go's direct mesh-query CPU path accounts for 0.15 and
0.22 sampled CPU seconds in the two UI windows; sampled totals are 2.29 and
3.35 seconds. Substantial native work persists without the external reads.
Public topology and traffic vary, so these windows do not yield an isolated
whole-application CPU percentage attributable to polling.

Omitting requests is a diagnostic counterfactual, not the application's current
desktop-minimize behavior: desktop polling continues when hidden. Group/channel
protocol work is list-driven and also stops with those reads. There is no
Flutter renderer in this probe; standard-output JSON adds transport overhead
that is different from the shipping FRB bridge. Neither native fixture matches
the owner's history, host or public neighbors.

## Current network work attribution

The standard recorder omits several envelope types, including peer announcements;
its event list alone cannot supply a complete traffic composition. A second
private compiler overlay therefore counts decoded inbound JSON envelopes after
unmarshal and successful direct-session writes after `WritePacket`. It retains
only type/count/size. The ordinary recorder periodically writes these counters.
Malformed packets, handshakes, other streams and OS overhead are outside them.
No payload logging or production-source change is introduced.

The same acknowledged 8-DM/2-group/1-channel fixture completes a 180–300 s
observation window with fourteen peers throughout. Message goldens match and
the debug bus reports zero dropped events. The topic snapshot has 32 local
topics, including 24 control/data/blob topics for the eight DMs. Classified
JSON envelopes account for 1,528,835 inbound and 827,778 outbound bytes. Their
combined rate is 0.157 Mbit/s; this is not a full wire-byte rate.

| Classified work in 120 s | Count | JSON bytes |
| --- | ---: | ---: |
| Outgoing GRAFT / incoming PRUNE | 1,728 / 1,728 | 88,128 / 88,128 |
| Outgoing `ov_find_value` / incoming `ov_values` | 367 / 367 | 46,976 / 682,226 |
| Outgoing `ov_find_node` / incoming `ov_nodes` | 213 / 213 | 27,051 / 370,527 |
| Outgoing `ov_store` | 424 | 103,544 |
| Incoming / outgoing peer announcements | 566 / 519 | 212,651 / 189,476 |

Overlay value/node replies account for 68.86% of classified inbound JSON bytes,
while peer announcements account for 13.91%. No outgoing publish envelope
occurs in this window. This does not mean all application protocol activity is
absent: directed and relayed control paths are separate types.

Source inspection explains recurring work without inventing a broken backoff:
unknown-topic speculative GRAFTs retry per peer/topic, a starved topic runs
overlay rendezvous every fifteen seconds, and the publishing loop refreshes
one provider record per subscribed opaque topic every thirty seconds. One DM
subscribes to control, data and blob channels, so saved offline DMs multiply
these tasks even when no user sends a message. The current PRUNE gate bounds
retries; it does not stop this repeated search.

## Single-process discovery counterfactual

A separate private overlay skips only `maybeDiscoverTopicPeers` for the exact
24 channels returned by eight established DM snapshots with known counterpart
IDs. The existing subscription table maps opaque topics back to those channels;
no raw-prefix assumption is made. Subscription handling, GRAFTs, provider
publication, peer-identity discovery, normal DM service and every other room
remain active. The ordinary recorder is disabled equally throughout this run.

After 180 seconds of warmup, the same native process measures three 60-second
windows: ordinary behavior, omitted known-DM rendezvous, ordinary behavior
restored. Each mode change has a 22-second settling interval outside the
measurement, exceeding the original twenty-second lookup timeout. The fixture
message golden matches throughout; each window begins and ends with twelve peers.

| Native window | DM rendezvous starts | Other rendezvous starts | Inbound / outbound classified JSON bytes | Combined classified rate |
| --- | ---: | ---: | ---: | ---: |
| Ordinary, first | 96 | 32 | 777,674 / 440,417 | 0.162 Mbit/s |
| Omit known-DM rendezvous | 0 | 32 | 449,132 / 427,530 | 0.117 Mbit/s |
| Ordinary, restored | 96 | 32 | 782,475 / 491,020 | 0.170 Mbit/s |

Value-reply bytes are 413,010 → 114,239 → 409,475. The selective query reduction
and its reversal identify known-DM topic rendezvous as a generator of repeated
work. The public neighbors and unrelated traffic are not frozen. These are
monotonic decoded/successful-write JSON-envelope counters, not OS wire totals,
and no whole-owner CPU reduction or shipping compatibility is established.
No recipient-return, linked-device or mixed-version acceptance is claimed by
an idle-history golden. This counterfactual is not enabled in a delivered build.

An additional measurement correction matters: `sessionByteTotals` sums only
currently live session counters. Replacing/removing a session can decrease that
sum even if peer count stays constant; the counterfactual observes a negative
delta. Live-session deltas are therefore excluded from the native rate tables
above. This limitation also applies when interpreting earlier native carrier
figures in this investigation. The owner's and Windows runner's ETW totals are
independent of this helper and remain reconciled, complete OS measurements.

This establishes a reproducible remaining network-work contributor, not the
composition of the owner's Windows traffic or the entire CPU cause. The
[proposed known-peer DM boundary](issue-94-dm-discovery.plan.md) requires a new
Moss-source/API approval before implementation; it is not an implemented fix.
