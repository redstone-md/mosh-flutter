# Plan: integrate moss v0.8.30

Upstream reference: this slice follows the interview in this session
(no separate brainstorm — the direction was chosen there: bump, verify, no
functional rewrite). Scratchpad: `.scratch/moss-v0.8.30-followups.md`.

## Goal and scope

Bump the vendored moss submodule from v0.8.19 (2026-07-29) to v0.8.30
(2026-09-16) and prove Mosh still works end to end.

In scope:
- Submodule bump v0.8.19 → v0.8.30 (tag; the v0.8.30 commit is a squash that
  already contains the changelog 0.8.31 entry and its fix — see
  `internal/transport/udp_handshake.go` conditional reap).
- Remove the hardcoded Axiom keys from `node_config_json`
  (`mosh-core/src/moss_ffi.rs`): moss's sink is opt-in; a Mosh client ships
  nothing by default.
- Adopt mesh event codes 8–11 (`message_delivered`, `message_read`,
  `typing`, `presence`) in `SnapshotEvent::name_for` + tests.
- Remove the dead pin mechanism: `moss.config.json` (stale v0.8.14) and
  `scripts/moss-update.mjs` (imports from the removed React app). The
  submodule pointer becomes the single canonical pin.
- Docs: ADR-0002 (pin = submodule), ADR-0015 (inherited-pin paragraph),
  CHANGELOG `[Unreleased]`, Architecture.md moss references if any.

Out of scope (follow-up slice, see scratchpad):
- Directed sends (`Moss_SendToPeer` family) as a DM-transport alternative.
- Streams (`Moss_OpenStream` family) for attachments.
- `Moss_Version` / `Moss_PeerRTT` surfacing in diagnostics.
- Anything on moss `origin/main` past v0.8.30 (masq, uTLS) — unreleased.

## Constraints and risks

- FFI surface is stable: all 28 `Moss_*` symbols used-or-available at
  v0.8.19 keep identical signatures at v0.8.30; mosh-core uses 20 of them.
  No `api::` change → no flutter_rust_bridge codegen.
- Error codes (-1..-14), `MeshInfo` JSON keys, config JSON keys: unchanged.
  Config parser stays lenient to unknown fields (verified at v0.8.30 source).
- Risk: announce jitter + empty-round doubling (v0.8.23) may lengthen
  tracker discovery; probe-e2e TIMEOUT=180 may need headroom on a quiet
  network. Watch, do not preemptively retune.
- Risk: cargo tests dlopen the real `libmoss.so` (8 files); a behavior change
  upstream can surface as a red baseline. Track each failure in the section
  below; fix one at a time.
- Local go is 1.27; moss pins `GOTOOLCHAIN=go1.25.9` in moss-prepare — go
  auto-downloads the pinned toolchain, no conflict.
- Go toolchain pin unchanged between v0.8.19 and v0.8.30 (verified in go.mod).

9. [x] probe-e2e on the stand (SSH given: World8 = Ubuntu 24.04, stand2 =
   51.91.214.115 = Debian 13; both x86_64). Deployed mosh-probe v0.8.30 +
   libmoss.so to /opt/mosh-stand on both. Results (v0.8.30 on both ends):
   - **dm: 4/5 delivered** (World8 delivered x2, stand2 delivered x3... of
     which one earlier control run; one World8 run failed on the ACK return
     path — see analysis).
   - **group: 3/3 received** (World8 x1, stand2 x2 — group is judged by the
     listening end).
   - **channel: 0/6 received** (both stands) — see the analysis; a
     pre-existing probe-gate defect plus this machine's NAT shape, not a
     v0.8.30 regression of the channel flow itself.

   Channel analysis (probe-timeline forensics):
   - The dialer gate fires when `mesh.peer_count > 0` — that counts
     SUBSTRATE peers (mossspore relay and strangers), not channel members.
     The send publishes into a topic mesh that is still empty → moss
     correctly refuses with `MOSS_ERR_NO_PEERS` (ADR-0021 semantics).
   - In every failing run the two probe ends **never held a substrate
     session with each other** (no peer_joined events between the two IPs).
     A channel has no invite and so no counterpart identity: it relies
     entirely on overlay rendezvous (findChannelPeers → hint dial), which
     needs sessions with the right core contacts. This local machine is a
     container behind port-restricted NAT holding ~12 stranger sessions;
     the lookup could not reach the record holders in 240s. DM/group carry
     the counterpart moss id and dial it explicitly — which is why they
     deliver.
   - v0.8.30 does change the failure's texture (graft throttles, PRUNE
     meshBlocked, 30s refreshLocalSubscriptions safety net vs 0.8.19's
     ~1s unconditional grafts): topic-mesh convergence for identity-less
     channels is now slower and more honest. The probe gate was racy all
     along — 0.8.19 masked it by storm-grafting strangers into the topic
     mesh fast enough for the send to find a target. Note there is no
     recorded evidence of a green channel probe run in this repo's history
     (probe-e2e was never in CI), so "it worked on 0.8.19" was never
     proven here either.
   - The one DM failure: the message WAS received by the remote (remote
     verdict ok:true, messages:1) but the local session died on missed
     pings ~34s in and was not re-established inside the window, so the ACK
     never came back and the dialer judged delivery failed. Related
     upstream changes: failure-charged redial backoff, bounded
     refreshExternalAddress (3 peers), coord-retry limits, median port
     prediction. Worth watching on NAT'd pairs; 4/5 delivered here.
   - Follow-ups filed (scratchpad): probe gate must wait for topic
     readiness, not substrate peers (needs an FFI surface for per-topic
     mesh, or a heard-from-counterpart gate); consider an upstream report
     about NAT-pair session re-establishment latency.
