# Android: сопоставимый baseline Mosh

Коллектор дополняет [существующие измерения Windows](README.md). Он читает
системные агрегаты через `adb`, не перезапускает Mosh, не меняет настройки,
не сбрасывает batterystats, не пишет logcat, изображения, сообщения или ключи.
Нужны Python 3.10+ и [Android Platform Tools](https://developer.android.com/tools/releases/platform-tools).
На Windows используй `py -3` вместо `python3`.

## Один замер

1. Установи подписанную release ARM64 сборку на настоящий телефон. Разреши
   отладку своему компьютеру. `adb devices` должен показывать один `device`,
   либо передай `--serial АДРЕС` для выбора. Серийный номер в отчёт не попадёт.
   Поддерживается основной Android-пользователь, не рабочий профиль.
2. Для батареи отключи зарядку и USB: используй
   [Wireless debugging](https://developer.android.com/tools/adb#wireless-android11-command-line).
   Держи компьютер включённым. ADB сам влияет на телефон; этот замер
   не доказывает прохождение настоящего Doze или задержку звонка.
3. Открой нужный экран Mosh. Запиши число сохранённых личек, групп, каналов
   и пиров из статуса соединения. Не начинай звонки и передачи файлов.
4. Из корня репозитория выполни, подставив свои количества:

   ```sh
   python3 scripts/network-diagnostics/android-baseline.py --output /tmp/mosh-android-offline-chat-01 --network wifi --ui chat --screen on --profile offline --peers 13 --dms 8 --groups 2 --channels 1
   ```

   На Windows для `--output` укажи, например, `C:\moshdiag\android-offline-chat-01`.
   Каталог должен быть новым. По умолчанию идут 120 секунд прогрева, затем
   180 секунд замера. `--warmup` и `--duration` задают другие интервалы.
   Состояние приложения и сети в это время сохраняй неизменным.
5. Дождись `Report ready`. Передай только `mosh-android-baseline.zip` из
   напечатанного каталога. В архиве один `report.json`: версия и SHA-256 APK,
   модель/ОС, выбранный сценарий, длительность и доступные агрегаты.

Прерывание Ctrl+C не оставляет системную запись работающей. Если телефон
отключился или отказал в доступе, метрики будут `unavailable`; ошибки не
превращаются в нулевой расход. После сбоя команд во время замера повтори
его с теми же условиями и новым выходным каталогом.

## Что означают метрики

| Поле | Граница измерения и ограничения |
| --- | --- |
| `cpu` | Дельта CPU главного процесса, если Android разрешил `/proc`. 100% — одно ядро. При пересоздании процесса результат недоступен. |
| `network` | Дельта истории RX/TX bytes/packets **UID** Mosh. Это не отдельный процесс; Android обновляет историю с задержкой. Нулевой результат не доказывает отсутствие трафика. Скорость в Мбит/с из этих данных не вычисляется. |
| `wakelocks` | Изменение суммы partial-wakelock времени UID в мс, если ОС его раскрыла. Перекрывающиеся блокировки могут считаться вместе. |
| `wakeups` | Счётчик wakeup alarms APK, если он присутствует в batterystats. Это не все пробуждения ядра или радио. |
| `battery` | Начальные/конечные уровень, charge counter и питание всего телефона, если доступны. Дельта не приписывается одному Mosh. Подключённая зарядка делает сравнение расхода некорректным. |
| `process_network`, `kernel_wakeups` | Честно недоступны: используемые nonroot интерфейсы не дают такой атрибуции. |
| `screen_observed` | Только состояния экрана в двух крайних точках; не доказательство неизменного состояния весь интервал. |

Сведения о сети, UI, ожидании и количествах задаёт оператор. Коллектор не
читает чаты и не проверяет эти утверждения по данным приложения. Он удаляет
SSID, адреса, список чужих приложений, имена wakelock/service и сырые dumpsys
из результата, сохраняя только выбранные поля. APK-хеш может отсутствовать,
если телефон не разрешил его чтение; такой отчёт не подтверждает бинарник.

## Матрица сравнения

Сохрани длительность, сборку, устройство, яркость, сеть, питание и количества
одинаковыми. Для каждого состояния сделай несколько отдельных прогонов:

| Профиль | Состояния |
| --- | --- |
| Пустой аккаунт | Список чатов, затем минимизация с выключенным экраном. Нужен отдельный тестовый профиль без удаления рабочего. |
| Доступные собеседники | Список, открытый чат, минимизация; `--profile online`. |
| Недоступные собеседники | Те же три состояния, `--profile offline`. |
| Смешанный профиль | Лички, группы и канал, `--profile mixed`. |

Для минимизации используй `--ui minimized --screen off`. После реализации
waiting повтори ту же матрицу с `--waiting enabled` и `--waiting disabled`;
этот параметр **только описывает** реальное состояние Mosh, не переключает его.
Текущий baseline использует `--waiting baseline`.

Запуск/догрузка измеряются отдельно: `--phase startup --warmup 0`. Начни
запуск Mosh после сообщения `Collecting`, выполни обычную разблокировку.
CPU может быть недоступен, если в первой точке процесса ещё не было.
Не сравнивай этот прогон со steady idle. Доставку сообщения и звонка измеряй
отдельными сценариями с независимым отправителем; этот скрипт её не проверяет.

Для desktop используй существующие `Start.cmd` / `Start-CPU.cmd` и одинаковую
матрицу. Их process-метрики нельзя выдавать за расход Android. Если Android
не раскрывает точные process bytes или wakeups, необходим отдельно
согласованный инструментированный замер, а не подстановка UID как процесса.

Baseline IVO-147 и численные budgets остаются незавершёнными, пока нет реальных
сопоставимых архивов телефона/desktop и согласованных целей. `acceptance_complete`
всегда `false`: успешный запуск коллектора не закрывает приёмку.

Форматы проверены по [документации dumpsys](https://developer.android.com/tools/dumpsys)
и [AOSP Android 16 BatteryStats](https://github.com/aosp-mirror/platform_frameworks_base/blob/android16-release/core/java/android/os/BatteryStats.java).
Проверка самого коллектора без телефона:

```sh
python3 -m unittest discover -s scripts/network-diagnostics -p 'test_android_baseline.py'
```
